# aspnetcore-aot — TechEmpower r23 Plaintext #10 (27,770,995 req/s)

## Summary
This is ASP.NET Core's **Platform-level** benchmark (project `src/Platform`, `PlatformBenchmarks.BenchmarkApplication`) — Kestrel's HTTP server with the entire MVC/middleware/routing stack *removed*, hooked directly onto the raw connection transport (`connection.Transport.Input/Output` Pipes), then compiled with **NativeAOT**. The one-line reason a managed runtime keeps up with C/Rust here: the hot path never allocates and never formats anything at request time — responses are **precomputed `u8` byte-literal preambles + a once-per-second cached Date header**, written into a `PipeWriter`-backed span, and an entire **pipelined batch of requests is coalesced into one flush** — while NativeAOT + ServerGC + source-generated JSON remove startup/JIT/reflection overhead so the steady state is effectively a tight memcpy loop. The managed runtime is almost entirely out of the per-request path.

## Architecture
- **Concurrency model:** Default Kestrel **Sockets transport** (`webHostBuilder.UseSockets(...)`, `research-sources/09-aspnetcore-aot/src/Platform/Program.cs:81-89`). On Linux this is backed by `SocketAsyncEngine` (epoll event loop) feeding a configurable number of **IO queues** (`options.IOQueueCount = threadCount`, set from the `threadCount` setting in `BenchmarkConfigurationHelpers.cs:25-27`; default ≈ processor count). Each connection is an `async` state machine (`BenchmarkApplication.ExecuteAsync`/`ProcessRequestsAsync`, `BenchmarkApplication.HttpConnection.cs:26-64`).
- **I/O mechanism:** **epoll via the managed `SocketAsyncEngine`** (readiness-style event loop dispatching pooled `SocketAsyncEventArgs`), *not* raw epoll syscalls in app code. Buffering is **System.IO.Pipelines** zero-copy: `PipeReader.ReadAsync()` yields a `ReadOnlySequence<byte>` parsed in place; `PipeWriter.GetSpan()/Advance()` is the write side. Critically, `options.UnsafePreferInlineScheduling = true` on Linux (`Program.cs:85-88`) makes read completion, parse, response build, and flush all run **inline on the epoll/IO thread** — no thread-pool hop per request. `WaitForDataBeforeAllocatingBuffer = false` skips the lazy-buffer round-trip.
- **Worker/process model:** **Single process**, N IO threads/queues (one epoll engine + IO-queue fan-out). This is NOT the SO_REUSEPORT-per-worker model — the default Sockets transport has one accept path; SO_REUSEPORT multi-accept is a property of the separate experimental `kestrel-linux-transport`, not what this benchmark runs (upstream, marked below). No explicit CPU affinity in the source; placement is left to the .NET thread pool / OS. `System.Threading.ThreadPool.HillClimbing.Disable=true` under AOT (`Platform.csproj:27-29`) pins thread-pool sizing.
- **HTTP parser:** Kestrel's internal **vectorized `HttpParser<ParsingAdapter>`** (`Microsoft.AspNetCore.Server.Kestrel.Core.Internal.Http`, used at `HttpConnection.cs:24,119-127`) — `ParseRequestLine` / `ParseHeaders` over the `SequenceReader<byte>` using SIMD (`System.Numerics.Vector`/intrinsics) to scan multiple bytes per instruction. The app's header callbacks (`OnHeader`, `OnHeadersComplete`) are **empty** (`HttpConnection.cs:164-177`) — it parses the request line only enough to route on the path bytes (`OnStartLine` → `GetRequestType`, `BenchmarkApplication.cs:91-131`) and ignores all headers. **Pipelining** is handled by the parser+loop: `HandleRequests` (`HttpConnection.cs:66-98`) loops parsing/processing every complete request in the buffer before a single `writer.Commit()` + `FlushAsync`.

## Performance techniques (catalog)
- **Pipelining & response coalescing.** `HandleRequests` (`src/Platform/BenchmarkApplication.HttpConnection.cs:66-98`) parses *every* pipelined request in the current `ReadOnlySequence<byte>` in a `while(true)` loop, appending each response into the **same** `BufferWriter`, then `writer.Commit()` once and a single `await Writer.FlushAsync()` in `ProcessRequestsAsync` (`:62`). N pipelined GETs → 1 flush → ideally 1 syscall/segment. This is the dominant lever behind the ~28M plaintext number (TFB pipelines plaintext at depth 16).
- **Syscall amortization / gathered writes.** Writes go through `PipeWriter` (`WriterAdapter`, `HttpConnection.cs:206-221`) with `sizeHint: 160 * 16` (`:69`) — sized for 16 pipelined plaintext responses so the whole batch lands in one pipe segment, flushed via the Sockets transport's gathered/`Advance`+`FlushAsync` path.
- **Allocation: zero-alloc steady state.** Responses are static `ReadOnlySpan<byte>` **UTF-8 literals** (`"...\r\n"u8`, `BenchmarkApplication.cs:20-40`, `.Plaintext.cs:12-16`) `memcpy`'d into the pipe span. The `BufferWriter<T>` is a `ref struct` (stack-only, `BufferWriter.cs:10`). Number formatting uses a branch-on-magnitude integer-to-ASCII with magic-multiply div (`WriteNumeric`, `BufferWriter.cs:97-141`) — no `int.ToString`. JSON uses a `[ThreadStatic]` reused `Utf8JsonWriter` (`.Json.cs:34-35`). Chunked writers are pooled (`DefaultObjectPool<ChunkedPipeWriter>`, `BenchmarkApplication.cs:44-56`). Pipelines buffers come from a pooled `MemoryPool`, not per-request `new`.
- **Response precomputation / cached Date header.** The whole status line + `Server: K` + `Content-Type` + `Content-Length: 13` is one precomputed literal (`_plaintextPreamble`, `.Plaintext.cs:12-16`). The **Date header is computed once per second on a background `Timer`** and atomically swapped via a double-buffer (`DateHeader.cs`: `s_headerBytesMaster`/`s_headerBytesScratch`, `Utf8Formatter.TryFormat(... 'R')`, tuple-swap at `:63`). The request path just `writer.Write(DateHeader.HeaderBytes)` — no per-request date formatting. This is Kestrel's `DateHeaderValueManager` pattern reproduced locally.
- **Platform-level bypass of MVC/middleware.** `UseHttpApplication<BenchmarkApplication>()` (`HttpApplication.cs`, `Program.cs:74-77`) registers the app as a raw **connection middleware** operating on `connection.Transport.Input/Output` — bypassing routing, model binding, `HttpContext`, filters, the HTTP/1.1 `HttpProtocol` request-object machinery, everything. `Startup.Configure` is **empty** (`Startup.cs`). Routing is a hand-written `GetRequestType` that compares path bytes with `SequenceEqual`/length checks (`BenchmarkApplication.cs:96-131`) — no dictionary, no regex, no allocation.
- **SIMD/vectorized parsing.** Kestrel's internal `HttpParser` uses `System.Numerics.Vector`/hardware intrinsics to scan request line and header bytes multiple-at-a-time (upstream `HttpParser.cs`, marked below). The app skips header *handling* entirely (empty `OnHeader`), so parsing cost is just the vectorized line/header scan.
- **Build / runtime.** `PublishAot=true`, `OptimizationPreference=Speed`, `GarbageCollectionAdaptationMode=0` (`aspnetcore-aot.dockerfile:6`). NativeAOT → ahead-of-time native code, no JIT warmup, no startup tier, smaller/faster, trimmed. **ServerGC** (multi-heap, throughput-tuned; standard for these benchmarks) + `HillClimbing.Disable=true` (`Platform.csproj:28`). **Source-generated JSON** (`JsonSerializerContext`/`[JsonSerializable]`, `BenchmarkApplication.cs:67-75`) = reflection-free, AOT-compatible serialization. Invariant globalization is the norm for these AOT images (no ICU). `Server: K` (one byte) trims response size.

## What's reusable for jai-http
- **Cached Date header (b — portable, HIGH leverage).** Directly portable and a clean win. Today jai-http formats per response; instead, a single owner (or one atomic pointer / double-buffered byte block) holds the 35-byte `"\r\nDate: ...\r\n"` string, refreshed once/second by a timer or by the epoll loop checking a coarse clock. Workers just `memcpy` the current bytes into the writev iovec. Maps cleanly onto the actor pattern (owner thread regenerates; workers read a published immutable buffer) or a lock-free atomic-pointer swap exactly like `DateHeader`'s master/scratch flip.
- **Precomputed response prefix / status-line literals (a/b — already partly done, HIGH leverage to extend).** jai-http already sends a fixed `"Hello, World!"`; the technique to *adopt* is baking the **entire constant header block** (status line + Server + Content-Type + fixed Content-Length) as a single compile-time byte literal and only varying Date + body. For a static-file handler this means precomputing per-file the full header (Content-Type + Content-Length) once at `#run` time, so the hot path concatenates [precomputed-header][cached-date][body] into one writev.
- **Pipelining + response coalescing (b — portable, HIGH leverage; our writev lever).** This is the single biggest delta vs jai-http's current design and the reason these leaders hit ~28M. The mapping: when a worker's read buffer contains *multiple* complete pipelined requests, parse and generate *all* their responses into one contiguous output (or one iovec array) and emit a **single writev**, instead of one writev per request. jai-http already has the writev primitive and a per-request Pool — extend the dispatch loop to "drain all complete requests in the buffer, accumulate responses, flush once" (mirrors `HandleRequests` → one `Commit`/`FlushAsync`). Low risk, high payoff under pipelined load.
- **Inline scheduling on the IO thread (a — already done conceptually).** `UnsafePreferInlineScheduling=true` removes a thread-pool hop so parse/handle/write run on the epoll thread. jai-http's shared-nothing SO_REUSEPORT workers *already* run the full read→parse→dispatch→writev inline on the worker's epoll thread — so jai-http is structurally ahead here; nothing to import.
- **Vectorized request parsing (c — portable, lower leverage).** SIMD path scanning (find request-line/header delimiters multiple bytes per instruction) is portable to Jai via `Machine_X64`/intrinsics, but jai-http's zero-copy byte-at-a-time parser is not the bottleneck for tiny plaintext requests; revisit only after pipelining/Date wins land.
- **Zero-alloc integer formatting (c — portable, lower leverage).** The magic-multiply div-by-10 `WriteNumeric` (`BufferWriter.cs:97-141`) is a tidy pattern for Content-Length without a general formatter, but jai-http's Content-Length is constant for static responses; only matters for dynamic bodies.
- **Source-gen JSON, NativeAOT, ServerGC, invariant globalization, ThreadPool tuning (d — .NET-specific).** Runtime-removal techniques with no Jai analog — jai-http is already AOT-native with manual memory; these are how *managed* code claws back to native parity, not techniques jai-http needs.

**Highest-leverage takeaways for jai-http:**
1. **Pipelining + response coalescing** — drain all complete requests in the read buffer and emit them in a single `writev`; this is the structural change that separates ~1.8M from ~28M on pipelined plaintext, and jai-http already has the writev + Pool primitives to do it.
2. **Cached, once-per-second Date header** (atomic/double-buffered, generated by an owner, memcpy'd by workers) — eliminates per-response date formatting for free and is trivially portable.
3. **Precompute the full constant header block as a byte literal** (especially per static file at compile time) so the hot path is purely `[const header][cached date][body]` concatenated into the iovec — keep the router/middleware off the hot path exactly as the Platform benchmark strips the MVC stack.

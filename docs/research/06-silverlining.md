# silverlining — TechEmpower r23 Plaintext #6 (27,962,675 req/s)

## Summary
silverlining is a low-level Go HTTP/1.1 framework that bypasses `net/http` entirely, talking to raw `net.Conn` with its own hand-written byte-scanning parser (`h1` subpackage) and its own response serializer. It stays fast *despite* Go's GC by being effectively zero-alloc in the steady state: per-connection 8KB read buffers, `Context` objects, and body readers all come from `sync.Pool`, and the request reader reuses one buffer across pipelined requests by compacting unconsumed bytes. The one-line reason it's fast: **it never touches `net/http`, parses HTTP with manual byte-scanning into pooled/reused buffers, and coalesces all pipelined responses into a single socket flush per read batch** — so the GC almost never runs on the hot path.

## Architecture
- **Concurrency model:** Goroutine-per-connection (classic Go blocking model), *not* a hand-rolled event loop. `ServeConn` runs a `for {}` loop that processes requests sequentially on one connection; each accepted connection gets its own goroutine. The performance does not come from a custom event loop — it comes from eliminating allocation and syscalls inside that loop. (upstream `silverlining.go` `ServeConn`)
- **I/O mechanism:** Linux `epoll` via the Go runtime's integrated netpoller — silverlining issues ordinary blocking `conn.Read`/`Write` calls and the runtime parks/unparks the goroutine on epoll readiness. There is no explicit `epoll_ctl`/`epoll_wait` in the project; it rides Go's transparent readiness poller. (upstream `server.go` uses `net.Listen` / `reuse.Listen`; no raw epoll syscalls)
- **Worker/process model:** Two modes. Default (`ListenAndServe`) is a single process with the normal Go scheduler. **Prefork** (`ListenAndServePrefork`, the mode the TechEmpower prefork entry uses — `silverlining-prefork.dockerfile` runs `./app -prefork`) forks `numCPU-1` child processes via `exec.Command(os.Args[0], …)` tagged with `SILVERLINING_PREFORK_CHILD` / `SILVERLINING_PREFORK_CHILD_ID` env vars; each child binds the *same* port through `reuse.Listen` (SO_REUSEPORT, `libp2p/go-reuseport`) and calls **`runtime.GOMAXPROCS(1)`** so every process is single-threaded and pinned to effectively one core's worth of scheduling — a shared-nothing one-process-per-core model that lets the kernel load-balance accepts across the SO_REUSEPORT socket group. (upstream `server.go` `ListenAndServePrefork` / `ListenAndServeReusePort`; vendored `src/main.go` `PreforkChildID` + `ListenAndServePrefork`)
- **HTTP parser:** Fully custom in the `h1` subpackage — **no `net/http`, no `bufio.Scanner`**. `RequestReader.Next()` calls `ParseRequestLine()` and `ParseHeaders()` which do manual byte scanning; on `ErrBufferTooSmall` it calls `Fill()` to read more from the socket and retries (with a `retryCount` guard). Pipelining is handled natively: `Remaining()` returns the count of bytes already read past the current request, so multiple requests arriving in one socket read are parsed back-to-back from the same buffer. (upstream `h1/reader.go` `Next`/`Fill`/`Remaining`, `h1/request.go`, `h1/headers.go`)

## Performance techniques (catalog)
- **net/http avoidance:** Server is built directly on `net.Listener`/`net.Conn`; request parsing and response serialization are hand-written in the `h1` package. This drops `net/http`'s per-request `*http.Request`/`*http.Response` allocations, header `map[string][]string`, and interface dispatch. Evidence: upstream `server.go` (`net.Listen`), `silverlining.go` (`ServeConn`), `h1/` subpackage; vendored handler uses `r.Path()` returning `[]byte` and `r.WriteFullBodyString` rather than `http.ResponseWriter` (`research-sources/06-silverlining/src/main.go`).
- **Custom byte-scanning parser + pipelining:** `h1/reader.go` `Next()` → `ParseRequestLine()` / `ParseHeaders()`; `Fill()` compacts unconsumed bytes to the front of the read buffer and reads more, so the same buffer serves a whole pipelined batch with no per-request allocation. `Remaining()` exposes leftover bytes for pipelining detection. (upstream `h1/reader.go`)
- **Write batching / response coalescing (the standout TechEmpower lever):** In `ServeConn`, responses accumulate in the `h1.Response` writer and the socket flush is *deferred*: it only calls `respW.Flush()` when `reqR.Remaining() == 0` (i.e., no more already-buffered pipelined requests) or when content length is unknown (`-1`). So an entire pipelined batch of requests produces **one `write()` syscall** for all their responses — massive syscall amortization, which is exactly what wins the heavily-pipelined TechEmpower plaintext test. Evidence: upstream `silverlining.go` `ServeConn` (`if reqCtx.reqR.Remaining() == 0 { err = reqCtx.respW.Flush() }`).
- **Allocation avoidance / GC dodging (zero-alloc steady state):**
  - 8KB read buffers from a `sync.Pool` (`buffer8kPool`, `getBuffer8k`/`putBuffer8k`), reset via `*b = (*b)[:cap(*b)]` and reused across connections. (upstream `silverlining.go`)
  - `Context` objects pooled in `requestPool` (`GetRequestContext`/`PutRequestContext` with `resetHard()`), so no per-request heap object. (upstream `silverlining.go`)
  - `BodyReader` instances pooled in their own `sync.Pool` in `h1`. (upstream `h1/reader.go`)
  - Single read buffer reused across all pipelined requests on a connection via `Fill()` compaction (an arena-like reuse). (upstream `h1/reader.go`)
  - This is the GC story: with buffers, contexts, and body readers all recycled, steady-state request handling produces near-zero garbage, so GC pauses essentially never fire on the hot path even though it's Go.
- **Response precomputation / Date caching:** `h1/fastdate.go` provides optimized HTTP date formatting (a cached, periodically-updated `Date:` header rather than re-formatting `time.Now()` per response — the standard high-perf server trick). (upstream `h1/fastdate.go`)
- **Faster JSON:** `WriteJSON` uses `goccy/go-json` (`github.com/goccy/go-json` in `go.mod`), a drop-in `encoding/json` replacement that is markedly faster and lower-alloc than stdlib. Note: `WriteJSON` itself calls `json.Marshal` (one allocation per call) — the json path is *not* zero-alloc, but plaintext is. Evidence: vendored `src/go.mod` (`goccy/go-json v0.10.5`); upstream `json.go`.
- **Prefork + SO_REUSEPORT + implicit core affinity:** `numCPU-1` single-threaded processes (`GOMAXPROCS(1)`) each on a SO_REUSEPORT socket; the kernel spreads connections across them, giving shared-nothing scaling and reducing cross-core contention and Go scheduler overhead. (upstream `server.go`; vendored `silverlining-prefork.dockerfile`)
- **Build flags / micro-arch tuning:** Both dockerfiles build with `GOAMD64=v3` (targets Haswell+ SIMD/instruction set) and `-ldflags="-s -w"` (strip symbols/DWARF — smaller binary, no runtime effect but signals a tuned release build). Evidence: `research-sources/06-silverlining/silverlining.dockerfile`, `silverlining-prefork.dockerfile`.
- **GC tuning (GOGC/GOMEMLIMIT):** **None found.** Neither dockerfile sets `GOGC`, `GOMEMLIMIT`, or `GOMAXPROCS` env vars, and the vendored sources contain no `debug.SetGCPercent`. Prefork sets `GOMAXPROCS(1)` *in code*, not via env. GC is left at defaults — the design avoids GC pressure by not allocating, not by turning GC off. (vendored dockerfiles; upstream code reviewed)

## What's reusable for jai-http

- **(a) Already done in jai-http:**
  - Shared-nothing **SO_REUSEPORT workers** — silverlining's prefork (one `GOMAXPROCS(1)` process per core on a SO_REUSEPORT socket) is the *exact same model* as our N shared-nothing SO_REUSEPORT workers, except we do it with threads + epoll inside one process instead of forked processes. Conceptually identical; nothing to port.
  - **Zero-copy parsing** — our zero-copy parser already mirrors their `h1` byte-scanning-into-buffer approach (string/byte views, no `net/http`-equivalent overhead).
  - **Per-request arena/Pool** — silverlining's GC avoidance via pooled `Context`/buffers and buffer-compaction reuse *is the moral equivalent of our per-request Pool allocator*; we already reset and recycle per request. We don't have a GC, so this is structurally free for us.
  - **Custom parser, no stdlib HTTP framework** — done.

- **(b) Portable + HIGH leverage:**
  - **Write batching / response coalescing across pipelined requests.** This is silverlining's single biggest TechEmpower win and a flagged jai-http gap. Mapping onto our stack: when an edge-triggered epoll read drains the socket and the zero-copy parser finds **multiple pipelined requests in one buffer**, dispatch them all, append each serialized response into one per-connection (or per-request-Pool) output buffer, and issue **one `writev`/`write` for the whole batch** — flushing only when no further buffered request remains (their `Remaining() == 0` condition). We already do single-`writev` per response; the lever is extending that to single-`writev` per *read batch*. This is the highest-impact item: it directly amortizes the write syscall that dominates at 28M req/s pipelined.
  - **Read-buffer compaction for pipelining (`Fill()` pattern).** Ensure our connection read buffer, after parsing N pipelined requests, compacts the unconsumed tail to the front and continues — reusing one buffer for the whole batch rather than re-reading or re-allocating. Pairs directly with the write-batching above; together they make a pipelined burst cost ~1 read + 1 write.

- **(c) Portable, lower leverage:**
  - **Cached/precomputed `Date:` header** (their `fastdate.go`): format the RFC1123 date once per second in a background tick (or lazily when the second changes) and `memcpy` it into responses instead of formatting per response. Cheap win once we emit a `Date` header; not on the critical path of the plaintext microbench but standard for a real server.
  - **Micro-arch build targeting** — their `GOAMD64=v3` analog is choosing an appropriate `-march`/target for the Jai release build on the Threadripper; minor, and orthogonal to architecture.

- **(d) Go-runtime-specific (not applicable to jai-http):**
  - `sync.Pool` and the goroutine-per-connection + netpoller model exist specifically to tame Go's GC and scheduler. We have neither a GC nor goroutines — our epoll event loop + per-request Pool already occupy that niche natively, so there's nothing to copy here; only the *intent* (recycle, don't allocate) transfers, and we already follow it.
  - `goccy/go-json` is a Go stdlib replacement; irrelevant to us (we have the vendored jaison JSON module). The transferable idea — serialize JSON directly into the per-request Pool buffer to avoid an intermediate copy — is already aligned with our Pool design.

**Highest-leverage takeaways for jai-http:**
1. **Implement pipelined response coalescing:** when one epoll read yields multiple pipelined requests, batch all their serialized responses into a single `writev`/`write` (flush only when the read buffer holds no further request). This is silverlining's decisive technique for the pipelined plaintext test and our biggest stated gap — it converts an N-request burst from N writes into 1.
2. **Compact-and-reuse the connection read buffer across a pipelined batch** (their `Fill()` pattern), so a burst costs ~1 read + 1 write with no per-request allocation — natural fit for our per-request Pool / zero-copy parser.
3. **Cache the `Date:` header** (precompute once per second) for the eventual real-server path — low cost, standard high-perf-server hygiene.

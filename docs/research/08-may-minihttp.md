# may-minihttp — TechEmpower r23 Plaintext #9 (27,906,423 req/s)

## Summary
may-minihttp is a tiny HTTP/1.1 micro-framework (`may_minihttp` 0.1.11) layered on **may** (0.3.51), a Go-style **stackful-coroutine** runtime for Rust with an M:N scheduler over epoll. The TFB entry's own `src/main.rs` is just a handler — all the speed lives upstream in the framework + runtime: the connection loop **drains every pipelined request out of one read buffer, appends every response into one write buffer, and flushes with a single write syscall**, while the `Date` header is pre-formatted once every 500 ms by a background coroutine instead of per request. The one-line reason it's fast: **per-connection syscall amortization (batched reads + coalesced writes) on a cheap green-thread-per-connection model, with a zero-alloc steady state.**

## Architecture
- **Concurrency model:** Stackful coroutines (`may`) — "the Rust version of the popular Goroutine" (upstream README). The server spawns **one coroutine per accepted connection**; the handler is written in straight-line blocking style (`stream.read`, `stream.write_all`) and the runtime transparently parks/resumes the coroutine on I/O readiness. M:N scheduler: many coroutines multiplexed onto a configurable, small set of OS worker threads ("Support schedule on a configurable number of threads for multi-core systems"). Coroutine stacks are pooled and tiny — `main.rs:285` sets `may::config().set_pool_capacity(1000).set_stack_size(0x1000)` (4 KB stacks, 1000-deep coroutine pool), so spawning a connection coroutine is cheap and stack memory is recycled.
- **I/O mechanism:** epoll-based readiness on Linux (may lists "efficient asynchronous network I/O"; its `generator`/`may` stack uses an epoll reactor under the hood). Coroutines yield on `EWOULDBLOCK` and are rescheduled when the fd is ready — readiness model, not completion. The connection loop additionally does an opportunistic **non-blocking** read/write (`nonblock_write`) and only parks when the socket would block.
- **Worker/process model:** Single process, M:N — may runs N scheduler worker threads (defaults toward core count) and steals/distributes coroutines across them. This is **not** the SO_REUSEPORT shared-nothing model; it's a shared scheduler with green threads. The DB connection pool is sized to `num_cpus::get()` (`main.rs:291`) and each `HttpService` instance is bound to a connection by `id` (`new_service(id)`, `main.rs:277`), giving a per-core affinity *for DB connections* even though the HTTP coroutines themselves are scheduled M:N. No explicit CPU pinning in the vendored code; the build does pass `-C target-cpu=native`.
- **HTTP parser:** **httparse 1.10.1** (in `Cargo.lock`), driven by may_minihttp's internal `request::decode()` (upstream `src/request.rs`): `httparse::Request::new(...).parse_with_uninit_headers(buf, headers)`, switching on `httparse::Status::Complete(amt)` / `Partial`. On `Complete` it advances the read buffer by `amt` and loops to parse the **next** pipelined request from the same buffer; on `Partial` it returns `None` to wait for more bytes. Headers are parsed into a stack array of `MaybeUninit` (no per-request header heap alloc). **Pipelining is handled by reading N requests, generating N responses into one buffer, and writing once** (see Performance techniques).

## Performance techniques (catalog)
- **Pipelining + response coalescing (the headline win).** The connection loop in may_minihttp's `http_server.rs` parses requests in an inner `loop` until `decode()` returns `None` (buffer drained), calling `response::encode(rsp, &mut rsp_buf)` for each — **all responses append into a single `rsp_buf`** — then flushes the whole batch with one `nonblock_write(stream, &mut rsp_buf)` / `stream.write_all(&rsp_buf)`. So a TFB pipeline of 16 plaintext requests becomes ~1 read-drain + 1 write syscall instead of 16+16. This is the dominant reason a plaintext score is ~28M vs. our ~1.8M (we do one writev *per request*). Evidence: upstream `src/http_server.rs` connection loop; `src/request.rs` `decode()` advance-and-reloop.
- **Cached / precomputed Date header.** Upstream `src/date.rs`: a `static CURRENT_DATE` holds a pre-formatted **29-byte** date string; a background coroutine `may::go!(loop { may::coroutine::sleep(500ms); date.update(); })` refreshes it twice a second. `append_date(buf)` just `extend_from_slice`s the cached bytes — **zero time formatting on the request path**. Evidence: upstream `src/date.rs`, `src/response.rs` (`crate::date::append_date(buf)` called from `encode`).
- **Constant, minimal response framing.** `response::encode` writes a fixed status-line literal `"HTTP/1.1 200 Ok\r\nServer: M\r\nDate: "` (single-char `Server: M` to shave bytes), then the cached date, then `Content-Length: ` with the body length via `itoa` (no allocation). Evidence: upstream `src/response.rs`.
- **Syscall amortization.** Batched-read / batched-write per connection (above) plus opportunistic non-blocking I/O before parking — minimizes epoll round-trips per request under load.
- **Zero-alloc steady state / buffer reuse.** Read and write are `BytesMut` buffers reused across the connection's lifetime: `reserve_buf` tops the read buffer back up to ~8 KB only when free space drops below ~1 KB; `advance_mut(read_cnt)` after a read and `advance(len)` after a parse move cursors without reallocating. Header storage is a stack `MaybeUninit` array. Evidence: upstream `src/http_server.rs` buffer management.
- **Parser specialization (httparse).** `httparse` is a hand-tuned, SIMD-accelerated HTTP/1.x parser (SSE4.2/AVX2 fast paths for token/URI scanning); `parse_with_uninit_headers` avoids zeroing the header array. Evidence: `httparse 1.10.1` in `Cargo.lock`; usage in upstream `src/request.rs`.
- **Custom global allocator: mimalloc.** `main.rs:1-2` sets `#[global_allocator] mimalloc::MiMalloc`. Faster, lower-fragmentation allocs than the system allocator for the (rare) heap traffic that does occur. Evidence: `src/main.rs`.
- **Aggressive release build.** `Cargo.toml [profile.release]`: `opt-level=3`, `codegen-units=1`, `lto='thin'`, `panic='abort'`, `overflow-checks=false`, `debug=false`, `incremental=false`; dockerfile adds `RUSTFLAGS="-C target-cpu=native"` (`may-minihttp.dockerfile:9`) so the whole tree, including httparse's SIMD, compiles for the bench host's exact CPU. `log` pulls `release_max_level_off` (logging compiled out). Evidence: `Cargo.toml`, `may-minihttp.dockerfile`.
- **Tiny coroutine footprint.** 4 KB stacks + a 1000-entry coroutine pool (`main.rs:285`) keep per-connection memory and spawn cost low, so the green-thread-per-connection model stays cache-friendly at high connection counts.
- **(DB-path, not plaintext) per-core DB connections + pipelined queries.** `PgConnectionPool` builds `num_cpus` may_postgres clients, each `HttpService` binds one by `id`; `get_worlds`/`updates` issue all `query_raw`s first then collect — pipelining queries over the connection. Not relevant to plaintext but shows the same "batch then collect" instinct.

## What's reusable for jai-http

- **Pipelined-response coalescing — (b) portable + HIGHEST leverage.** This is the single biggest gap vs. the leaders and the main reason their plaintext number is an order of magnitude higher. Our edge-triggered epoll worker already reads into a per-connection buffer; the change is: after a read, **parse requests in a loop until the buffer is drained (Partial)**, dispatch each handler appending its full response into one per-connection output buffer, then do **one `writev`/`send` for the whole batch** instead of one writev per request. Maps cleanly onto our existing per-connection read buffer + Pool + writev. Caveat: must cap the batch / respect `MAX_*` and partial-write backpressure (mirror may's `reserve_buf` top-up + cursor advance). This alone should move us materially toward the top tier on pipelined plaintext.

- **Cached Date header — (b) portable + HIGH leverage (small, cheap, immediate).** We don't emit `Date` today, but any realistic server should, and formatting it per request is pure waste. Port directly: a single background thread (we already use raw `Thread` for actor/consumer patterns) writes a pre-formatted 29-byte RFC 1123 date into a shared buffer every ~500 ms–1 s; handlers `memcpy` the cached bytes. Our `datetime` module already has the formatting primitives; this is a few lines and removes time syscalls/formatting from the hot path. (may uses a coroutine + `UnsafeCell`; our equivalent is a thread + an atomically-published/`memcpy`'d byte slice — the *technique* is what ports, not the mechanism.)

- **Constant minimal response framing + `itoa`-style Content-Length — (a) mostly already done / (c) minor.** We already build headers cheaply via the Pool and writev. Worth borrowing: hoist the fixed status-line+`Server:`+`Content-Type:` prefix into a compile-time constant string and only format the variable `Content-Length` digits, so the common 200 path is `const-prefix + cached-date + small-int + body`. Low effort, low-to-moderate gain.

- **httparse SIMD parsing — (d) Rust-specific (technique portable, lower priority).** Our zero-copy parser is already a strength. SIMD-accelerating token/URI scanning is a *possible* future micro-opt for jai-http (Jai has `Machine_X64`/SIMD intrinsics), but it's deep in the noise compared to write batching; not a near-term win.

- **mimalloc / target-cpu=native / LTO — (a)/(d) build-level.** Our Pool allocator already removes per-request heap traffic (the analog of their zero-alloc + mimalloc combo). The build-flag analogs in our metaprogram: ensure the `-release` path is genuinely max-opt and consider a native-CPU codegen pass for benchmark builds. Already largely covered by our architecture.

- **Stackful-coroutine scheduling model — (d) may-specific, do NOT adopt.** may's M:N green-thread-per-connection scheduler is the *opposite* design from ours (callback-driven edge-triggered epoll + shared-nothing SO_REUSEPORT workers). Both are valid roads to the same place; our shared-nothing model already avoids the cross-thread scheduling/stealing overhead may pays. The lesson to extract is **not** the coroutine runtime — it's the *I/O batching behavior that runtime happens to make natural* (drain-many-requests, write-once), which we can implement directly in our event loop.

**Highest-leverage takeaways for jai-http:**
1. **Implement pipelined-request draining + single coalesced `writev` per read-batch** in the worker loop — the one change that closes most of the ~1.8M→tens-of-millions plaintext gap, and it slots straight into our per-connection-buffer + Pool + writev design.
2. **Add a timer-refreshed cached `Date` header** (background thread writes a 29-byte buffer every ~1 s; handlers memcpy it) — tiny effort, removes per-request time formatting, and makes us spec-compliant.
3. **Make the 200-OK response a constant header prefix + cached date + `itoa`-style Content-Length** so the hot path is concatenation, not formatting.

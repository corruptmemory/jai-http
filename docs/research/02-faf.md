# faf — TechEmpower r23 Plaintext #2 (28,034,705 req/s)

## Summary
faf ("Fast As F***") is a single-purpose Linux web server in **nightly Rust**, written by errantmind explicitly to "demonstrate the upper bound of possible single-node performance" (`research-sources/02-faf/README.md`). It is effectively **no_std + zero-dependency raw-syscall** code: one pinned thread per CPU core, each with its own SO_REUSEPORT listen socket steered by a cBPF program, a level-triggered epoll loop made entirely of inline-asm syscalls, and a **SIMD pipelined parser that coalesces N pipelined HTTP requests into one buffer and replies with a single write**. The one-line reason it hits 28M req/s: it removes essentially all per-request overhead (no libc, no allocator, no copies beyond a memcpy of a precomputed response) and amortizes syscalls across a whole pipelined batch.

Note on what was vendored: the TechEmpower entry here (`faf-ex`) is a ~80-line *harness* (`research-sources/02-faf/src/main.rs`) that pulls the real engine from `git = "https://github.com/errantmind/faf.git"` (`research-sources/02-faf/Cargo.toml`). The harness shows the response-construction strategy; the engine (epoll loop, sockets, parser) is **upstream** — those claims are marked [upstream] below.

## Architecture
- **Concurrency model:** Thread-per-core, shared-nothing. [upstream `src/epoll.rs`] spawns `for core in 0..num_cpu_cores` and pins each thread with `set_current_thread_cpu_affinity_to(core)` (wraps `sched_setaffinity`). Threads `unshare`/`CLONE_FILES` so each owns an independent fd table. No work stealing, no cross-thread comms.
- **I/O mechanism:** **epoll, level-triggered** (readiness model, *not* io_uring/completion). [upstream] epoll events are registered with `EPOLLIN` only — no `EPOLLET` — so it is level-triggered. The wait is a raw `SYS_EPOLL_WAIT`. There is **no io_uring and no SQPOLL** anywhere; the upstream README discusses only `epoll.rs` as the core. faf reaches 28M on plain epoll, which reframes the assumption that io_uring is mandatory at the top of the table.
- **Worker/process model:** Single process, **SO_REUSEPORT per-thread listen socket** with **`SO_ATTACH_REUSEPORT_CBPF` CPU-local steering** [upstream `src/net.rs`]. `attach_reuseport_cbpf()` attaches a 2-instruction classic-BPF filter: load the running CPU id via `SKF_AD_CPU` (ancillary offset 36) and `BPF_RET | BPF_A` it, so the kernel hashes each incoming connection to the reuseport socket **owned by the core it arrived on** — keeping the connection, its buffer, and its epoll instance all on one core (cache/NUMA locality). `TCP_NODELAY` is set per connection; `SO_REUSEADDR`, `TCP_QUICKACK`, `TCP_FASTOPEN`, `SO_ZEROCOPY` were tried and left commented out.
- **HTTP parser:** Custom, **SIMD, pipeline-aware** [upstream `src/epoll.rs`]. The read loop is `while request_buffer_offset != (read + residual) { parse_request_path_pipelined_simd(...) }` — it parses *every* request sitting in one `recvfrom` buffer, tracking a `residual` of unparsed bytes carried across epoll events. Pipelining is thus first-class: many requests per read, and (per the harness response construction) the responses are appended into one response buffer and sent with a single `sendto`. Only method+path are parsed (`memcmp` against `GET` and `/plaintext`); everything else is ignored.

## Performance techniques (catalog)
- **HTTP pipelining & response coalescing — the dominant lever.** [upstream `src/epoll.rs`] `parse_request_path_pipelined_simd` drains all pipelined requests from a single `SYS_RECVFROM` buffer; the harness `cb` (`research-sources/02-faf/src/main.rs:36-75`) writes each response into a response buffer via `copy_nonoverlapping`, and the engine flushes the batch in one `SYS_SENDTO`. TechEmpower's plaintext test sends up to 16 pipelined requests per connection, so this turns ~16 request/response syscall pairs into roughly **one recv + one send** — the single biggest reason the number is ~16× a non-pipelining server.
- **Syscall amortization via raw syscalls + no libc.** [upstream] Every syscall is issued through a `sys_call!` inline-asm macro with raw numbers (`SYS_EPOLL_WAIT`, `SYS_RECVFROM`, `SYS_SENDTO`, `SYS_ACCEPT`, `SYS_EPOLL_CTL`, `SYS_NANOSLEEP`) — no libc wrapper frames, no `errno` TLS dance. README: the project "has no Rust dependencies and can be converted into a `#![no_std]` project" producing "~400 lines of assembly TEXT, and 7KB binary" (`research-sources/02-faf/README.md`). It does **not** use writev/sendmmsg — it doesn't need to, because coalescing already produces one contiguous send.
- **Zero-allocation, fixed per-connection buffers.** [upstream] Buffers are statically sized and 64-byte aligned: `ReqBufAligned([u8; REQ_BUFF_SIZE * MAX_CONN])` and `ResBufAligned([u8; RES_BUFF_SIZE])` with `#[repr(align(64))]`. There is no heap allocator on the hot path (no_std-capable); request and response memory is a fixed arena indexed by connection. Cache-line alignment avoids false sharing across the per-core threads.
- **Response precomputation + cached Date.** (`research-sources/02-faf/src/main.rs:19-31`) The status line + `Server` + `Content-Type` + `Content-Length` are concatenated **at compile time** into `PLAINTEXT_BASE` via a `const_concat_bytes!` macro. At request time the handler does four `copy_nonoverlapping`s: the const base, then a **`date_buff` pointer handed into the callback** (the Date header is formatted once per second by a separate thread, not per request — `cb` takes `date_buff: *const u8`), then `CRLFCRLF`, then the const body. No formatting, no `Content-Length` computation, no per-request Date syscall (`clock_gettime`/`time` is amortized to ~1/sec).
- **CPU affinity / thread-per-core / NUMA locality.** [upstream] Covered above: `sched_setaffinity` per thread + cBPF `SKF_AD_CPU` steering keeps each TCP connection pinned to one core end to end. This is what lets it scale linearly across all cores without lock or cache-line contention.
- **Parser specialization / SIMD.** [upstream] `parse_request_path_pipelined_simd` — SIMD scan to locate path boundaries; only the bytes needed to route are touched. The harness then routes with branch-predicted `likely(...)` hints and raw `memcmp` (`research-sources/02-faf/src/main.rs:46-48`).
- **Build: maximally aggressive nightly toolchain.** (`research-sources/02-faf/faf.dockerfile`, `research-sources/02-faf/Cargo.toml`) `RUSTFLAGS="-Ctarget-cpu=native -Ztune-cpu=native -Zmutable-noalias=yes -Clto=thin -Copt-level=3 -Ccodegen-units=1 -Cpanic=abort -Cembed-bitcode=yes -Cdebug-assertions=no -Coverflow-checks=no ..."`, built with `-Zbuild-std=panic_abort,core,std,alloc,...` (rebuilds the standard library with the same flags / target-cpu), linked with `clang-15` + `ld.lld-15` + ThinLTO, then `strip`ped. `Cargo.toml` release profile reinforces: `opt-level=3, lto="thin", codegen-units=1, panic='abort', overflow-checks=false`. `target-cpu=native` lets the SIMD parser use the bench host's widest vector ISA.
- **Other:** README states the design priority order is explicitly **Speed > simplicity > memory safety** — unsafe Rust is used freely on the hot path (the harness body is one big `unsafe` block of raw pointer copies). `force-frame-pointers=n`, `control-flow-guard=no`, `link-dead-code=no` shave the last instructions.

## What's reusable for jai-http

- **HTTP pipelining + response coalescing — (b) portable, HIGHEST leverage.** This is the gap that separates ~1.8M from ~28M on the *plaintext* test, and it is independent of io_uring. jai-http already has the right substrate: a zero-copy incremental parser with string views into the connection read buffer, and a single `writev`. The change is to **loop the parser over the whole read buffer** (parse → dispatch → append response to an output buffer, repeat until the buffer is drained), carrying a `residual` of any partial trailing request to the next epoll event, then issue **one send for the whole batch**. Map onto existing pieces: the per-request Pool reset must move to *per-batch* (reset after the whole pipelined batch flushes, not per request), and the `writev` becomes a single write of one coalesced buffer (or an iovec array of the per-response slices). No new kernel facility required.
- **Precomputed response template + once-per-second Date — (b) portable, HIGH leverage, cheap.** faf builds the constant header bytes at compile time and only memcpys a cached Date pointer per request. jai-http currently formats the header per request through the Pool. Precompute the constant status-line/Server/Content-Type/Content-Length at startup (or via `#run`), keep a single Date string refreshed ~1/sec by a background thread (or lazily when the second changes), and reduce per-request work to memcpys. This also eliminates per-request `tprint`/`sprint` formatting entirely — directly relevant given the prior temp-storage collapse already root-caused in this project.
- **CPU affinity + `SO_REUSEPORT` cBPF steering — (b/c) portable, leverage grows with core count.** jai-http already does SO_REUSEPORT shared-nothing workers; it does **not** pin them or steer connections. On the 64-thread Threadripper target this is meaningful: add `sched_setaffinity` to pin each worker to a core, and attach the `SO_ATTACH_REUSEPORT_CBPF` `SKF_AD_CPU` filter so the kernel routes each connection to the reuseport socket on its arrival core — connection, buffer, and epoll instance stay on one core. Straightforward syscall/setsockopt work, no architecture change.
- **Fixed per-connection arena buffers — (a) largely already done.** jai-http's per-connection read buffer + per-request Pool already give zero-alloc-ish behavior; faf's static arena is the more extreme version. Worth noting only the 64-byte alignment of per-core/per-conn buffers to avoid false sharing.
- **Raw syscalls / no libc / no_std — (d) language-runtime-specific, low priority.** faf's 7KB no_std binary is a Rust flex; Jai links libc and that's fine per the project's stated non-goals. Skipping libc wrappers buys little next to pipelining. Not worth pursuing.
- **`-C target-cpu=native` + LTO + PGO-class flags — (c) portable, modest.** The Jai analog is building release with the most aggressive optimization the compiler offers; `target-cpu=native` mainly matters because it feeds faf's SIMD parser. Low effort, small win on its own.
- **io_uring — (b) portable but NOT the lever faf demonstrates.** faf proves you can reach the top of the table on **plain level-triggered epoll** with pipelining; io_uring is a *separate, additive* axis other top entries use (registered buffers/fds, SQPOLL, batched submission to cut syscalls further). For jai-http it remains a large, high-effort rewrite of the I/O core (completion model, fixed/registered buffers, ring management) — worth a dedicated study, but **pipelining is the cheaper and bigger first win**, and faf is the evidence for that ordering.

**Highest-leverage takeaways for jai-http:**
1. **Implement HTTP pipelining with response coalescing** (parse-all-in-buffer → append-all-responses → one send; reset Pool per batch). This is the dominant factor in faf's number and maps cleanly onto jai-http's existing zero-copy parser + writev. Do this before io_uring.
2. **Precompute the constant header bytes and cache the Date once per second**, reducing the hot path to memcpys and killing per-request header formatting/temp-storage pressure entirely.
3. **Pin workers (`sched_setaffinity`) and add the `SO_ATTACH_REUSEPORT_CBPF` `SKF_AD_CPU` steering filter** so each connection stays on one core — high return specifically on the 64-thread target.

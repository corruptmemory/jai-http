# pico.v — TechEmpower r23 Plaintext #4 (28,025,837 req/s)

## Summary
pico.v is a minimal HTTP benchmark app written in the V language (which transpiles to C and is then compiled by GCC), so the runtime is effectively hand-tuned C. The engine is two thin V wrappers over well-known C libraries: **picoev** (kazuho's epoll-based single-threaded event loop, originally from H2O's lineage) and **picohttpparser** (H2O's zero-copy, SSE4.2-accelerated HTTP request parser). It is fast because the request never leaves the read buffer (zero-copy parse), the parser scans 16 bytes per SIMD instruction, responses are essentially precomputed strings (including a cached `Date` header), and the whole thing is forked one-process-per-core with each process pinned via `taskset` and listening on a shared `SO_REUSEPORT` socket — a shared-nothing design nearly identical in spirit to jai-http.

## Architecture

- **Concurrency model:** Single-threaded event loop **per process** (picoev). There is no per-request threading, no thread pool inside a process, and no locks. Scaling is achieved by running N independent processes (one per logical core), each driving its own picoev loop. This is the same shared-nothing model jai-http uses, except jai-http runs N *threads* in one process whereas pico.v runs N *processes*.
- **I/O mechanism:** **epoll** on Linux (picoev abstracts over `select`/`epoll`/`kqueue`; on Linux it selects the epoll backend). Readiness-driven, non-blocking sockets. picoev stores per-fd callback state in a **flat array indexed by fd** (exploiting that Unix fds are small integers — O(1) lookup, no tree/hash) and tracks idle/timeout connections with a **ring buffer of bit-vectors** (a sliding wheel, ~128 slots advancing once per second) instead of a sorted timer structure. Upstream readme does not state level vs edge triggering explicitly; the array+ring-buffer design is the documented hot-path optimization.
- **Worker/process model:** **SO_REUSEPORT prefork, one process per logical CPU, each pinned.** `run.sh` literally does `for i in $(seq 0 $(($(nproc --all)-1))); do taskset -c $i ./main & done; wait` (`research-sources/04-pico.v/run.sh`). Each `./main` process calls `picoev.new(8088, &callback).serve()` (`research-sources/04-pico.v/main.v:40`) and binds the same port; the kernel `SO_REUSEPORT` hash spreads accepted connections across the per-core processes, and `taskset -c $i` pins process *i* to core *i* so each epoll loop has a dedicated, affinity-stable core. No inter-process communication.
- **HTTP parser:** **picohttpparser** (vendored into pico.v as the V module `syou.picohttpparser`, wrapping H2O's C). It is *stateless and zero-copy* — the caller passes the read buffer and an output struct, and the parser fills the struct with **pointers into that same buffer** (method, path, version, header name/value slices); it allocates nothing. The standout speed trick is `findchar_fast`, which uses the **SSE4.2 `PCMPESTRI` instruction (`_mm_cmpestri` in `_SIDD_CMP_RANGES` mode)** to test 16 bytes at a time against character ranges, scanning the URI and header lines a cache-line-and-a-half per instruction, with a scalar fallback for the <16 trailing bytes. The SIMD path is gated by `#if __SSE4_2__`, so it only activates when the C compiler targets a CPU with SSE4.2 — which the dockerfile's `-march=native` guarantees on the benchmark host. Pipelining is handled by the parser's `prevbuflen`/`last_len` resume parameter: multiple requests already sitting in one buffer are parsed in sequence without re-scanning consumed bytes. In `main.v` the handler routes by comparing raw buffer slices with `hp.cmpn(req.method, 'GET ', 4)` / `hp.cmpn(req.path, '/plaintext', 10)` — fixed-length `memcmp`-style prefix checks straight off the zero-copy pointers, no string allocation or routing table.

## Performance techniques (catalog)

- **Zero-copy parsing** — picohttpparser returns pointers into the read buffer; no per-request copy of method/path/headers. Evidence: upstream `https://github.com/h2o/picohttpparser` ("stateless and does not allocate memory by itself... setups the pointers... to point at the necessary portions of the buffer"); handler reads slices directly (`research-sources/04-pico.v/main.v:23-28`).
- **SIMD parser specialization (SSE4.2)** — `findchar_fast` uses `_mm_cmpestri` (`PCMPESTRI`, `_SIDD_CMP_RANGES`) to scan 16 bytes/instruction for control chars / range membership while parsing the URI and header lines; reported 68–90% parse speedup vs scalar. Gated by `#if __SSE4_2__`, enabled here by `-march=native`. Evidence: Kazuho's writeup `http://blog.kazuhooku.com/2014/12/improving-parser-performance-using-sse.html`; dockerfile flags (`research-sources/04-pico.v/pico.v.dockerfile:11`).
- **Response precomputation** — the plaintext body is a constant `'Hello, World!'` returned from an `[inline]` function; the JSON body is encoded but the struct is trivial. No templating, no per-request formatting of the body. Evidence: `research-sources/04-pico.v/main.v:9-20`.
- **Cached `Date` header** — the response builder calls `header_date()` (`main.v:25,28`). The HTTP spec requires a `Date:` header, and formatting it per-request is expensive; picoev/pico.v's idiomatic approach is to format the date string once per second (driven by the event-loop tick) and have every response in that second reuse the cached string. This removes a `gmtime`/`strftime` call from the per-request hot path. Evidence: `header_date()` usage in `research-sources/04-pico.v/main.v`; this is the standard picoev/H2O pattern (the same `Date`-once-per-tick trick jai-http has flagged as "not yet doing").
- **Builder-chain response assembly** — `res.http_ok().header_server().header_date().plain().body(...)` appends directly into the connection's output buffer in one pass, then a single write; analogous to jai-http's single `writev`. Evidence: `research-sources/04-pico.v/main.v:25,28`.
- **Allocation avoidance / buffer reuse** — parser allocates nothing; picoev reuses per-connection buffers across the connection's lifetime; the per-fd state array is preallocated. Evidence: parser docs (upstream); picoev array-based fd storage (`https://github.com/kazuho/picoev` readme).
- **CPU affinity + prefork-per-core** — `taskset -c $i ./main` per logical CPU; each process owns one core and one epoll loop. Eliminates cross-core cache bouncing and scheduler migration. Evidence: `research-sources/04-pico.v/run.sh`.
- **SO_REUSEPORT load balancing** — kernel-side connection distribution across the prefork processes; no userspace accept-lock contention. Evidence: each process independently binds port 8088 via `picoev.new(8088, ...)` (`research-sources/04-pico.v/main.v:40`) combined with the per-core prefork in `run.sh`.
- **O(1) event-loop bookkeeping** — flat fd-indexed callback array + ring-buffer timeout wheel instead of trees/heaps. Evidence: `https://github.com/kazuho/picoev`.
- **Aggressive build flags** — `v -prod -cflags '-std=gnu11 -Wall -O3 -march=native -mtune=native -flto'`. `-prod` is V's optimized mode; the underlying GCC build gets `-O3`, `-march=native`/`-mtune=native` (unlocks SSE4.2/AVX for the parser and lets GCC tune to the exact benchmark CPU), and `-flto` (link-time optimization, so the V-generated C, picoev, and picohttpparser inline across module boundaries). Evidence: `research-sources/04-pico.v/pico.v.dockerfile:11`.
- **Minimal routing** — fixed-length prefix `cmpn` comparisons, not a router. There is no path-param matching or middleware on the hot path. Evidence: `research-sources/04-pico.v/main.v:23-31`.

## What's reusable for jai-http

**(a) Already done in jai-http:**
- SO_REUSEPORT shared-nothing workers — jai-http already runs N workers each with its own epoll and its own reuseport socket. pico.v validates the architecture choice (it just uses processes instead of threads).
- epoll edge/readiness loop, non-blocking sockets — already core to jai-http.
- Zero-copy parsing — jai-http's parser already views into the connection buffer.
- Single coalesced write — jai-http's `writev([headers, body])` is the moral equivalent of pico.v's one-pass builder + single send.
- Per-request buffer/allocator reuse — jai-http's per-request Pool is its analog (pico.v leans on the stateless parser + reused connection buffers rather than a pool, but the no-per-request-heap-traffic goal is shared).

**(b) Portable + HIGH leverage:**
- **Cached `Date` header (format once per second).** This is the single cleanest win. jai-http currently formats/builds the response header per request and the project notes explicitly list "Date caching" as not-yet-done. Map: have one designated mechanism (a worker-shared atomic string pointer, or a per-worker string refreshed on the epoll tick when the second changes) hold the current `Date:` line; `write_response` memcpys that fixed-length string into the header instead of calling into the datetime module per request. Because jai-http already owns a datetime module and a per-request Pool, this is a small, isolated change with measurable per-request savings under load.
- **SSE4.2 SIMD scanning in the parser (`PCMPESTRI`/range-compare).** jai-http's zero-copy parser scans for delimiters (spaces, CRLF, header-name colons) byte-by-byte. picohttpparser's `findchar_fast` does the same scans 16 bytes per instruction. Map: jai-http can `#import "Machine_X64"` (already an allowed dependency per CLAUDE.md) to emit `pcmpistri`/`pcmpestri` or use a portable SWAR (SIMD-within-a-register, 8 bytes per u64 with bit-twiddling) fallback for the URI/header line scans, with a scalar tail for the last <16 bytes. High leverage because parsing is on the literal hot path for every request and the Threadripper target supports SSE4.2/AVX2. (SWAR is the lower-risk first step; true SSE4.2 intrinsics are the ceiling.)
- **`-march=native` / `-O3` / LTO equivalent at build time.** pico.v's parser speedup is partly *unlocked by the build flags* — the SIMD path is dead code without `-march=native`. jai-http should ensure its release build targets the host microarchitecture so any SIMD/SWAR parser code (and general codegen) actually uses the available instructions on the Threadripper. Map onto `first.jai`'s `-release` modifier: verify the optimized build path enables host-CPU targeting; this is a one-time build-config change that benefits the whole binary, not just the parser.

**(c) Portable, lower leverage:**
- **CPU affinity / pinning workers to cores.** pico.v pins each process with `taskset`. jai-http runs threads, so the analog is `pthread_setaffinity_np` (via POSIX/Linux modules) to pin worker N to core N. On a 64-thread Threadripper this can reduce migration/cache-bounce, but the win is hardware/load dependent and jai-http already noted CPU affinity as an untried lever; moderate, measure-it-first leverage.
- **O(1) connection bookkeeping (flat fd-indexed array + timeout wheel).** picoev's array-indexed-by-fd callback store and ring-buffer timeout wheel are elegant. jai-http already uses a connection pool with instance-bit recycling, which is close; a fd-indexed flat array is a possible micro-optimization for connection lookup, and a ring-buffer timeout wheel would be the right structure if/when jai-http adds idle-connection timeouts. Low urgency until timeouts are a feature.
- **Builder-chain that appends straight into the output buffer.** Stylistic; jai-http's writev already avoids intermediate copies, so limited additional gain.

**(d) Not portable / not applicable:**
- **Prefork *processes* vs threads.** pico.v's one-process-per-core model is a V/C-runtime choice; jai-http is deliberately threads-in-one-process with a per-request Pool. Don't switch models — the shared-nothing *benefit* is already captured with threads.
- **V → C transpile + `-flto` cross-library inlining.** This is V's toolchain story; jai-http is a single Jai program where the compiler already controls whole-program codegen, so there's no cross-module C-LTO problem to solve.
- **Trivial `cmpn` "routing".** pico.v has no real router; jai-http's chi-style router is a feature, not overhead to remove (its measured single-route overhead is ≈0). Not a technique to adopt.

**Highest-leverage takeaways for jai-http:**
1. **Cache the `Date` header and format it once per second**, then memcpy it into every response header — removes a per-request datetime call that jai-http currently pays and that pico.v explicitly avoids. Smallest change, clearest win, and it's already on jai-http's own "not yet doing" list.
2. **SIMD/SWAR-accelerate the zero-copy parser's delimiter scans** (SWAR first, SSE4.2 `PCMPESTRI` as the ceiling) — the same `findchar_fast` trick that gives picohttpparser 68–90% of its parsing edge, mapping directly onto jai-http's existing byte-at-a-time buffer scanning.
3. **Build for the host microarchitecture** (`-march=native`-equivalent + `-O3`/LTO-equivalent in the `-release` path) so the SIMD parser work above is actually emitted on the Threadripper instead of compiled out.

# uWebSockets.js — TechEmpower r23 Plaintext #5 (27,991,649 req/s)

## Summary
uWebSockets.js is a thin V8 native-addon binding (the `uWebSockets.js` npm package) over **uWebSockets** (a ~10k-line C++ HTTP/WS server) sitting on **uSockets** (the C socket + event-loop layer). Almost no JavaScript runs on the hot path: the plaintext route is served by a **`DeclarativeResponse`** — a fully precomputed response (status line + headers + body) constructed once at startup and replayed by the C++ engine per request, so V8 is never re-entered to format or send the reply. The speed comes from C++ doing the parsing, header assembly, and a single corked `send()`, while Node's `cluster` module forks one process per core over `SO_REUSEPORT` for linear multi-core scaling.

## Architecture

- **Concurrency model:** One Node.js process per CPU core (`cluster.fork()` × `os.availableParallelism()` in `clustered.js`), each running its **own uWebSockets event loop** (uSockets `us_loop`). Within a worker everything is single-threaded and event-driven — the standard "shared-nothing process per core" model, not threads. JS handlers are only invoked for the dynamic routes (`/json`, `/db`, etc.); the benchmarked plaintext route bypasses JS entirely via `DeclarativeResponse`.
- **I/O mechanism:** uSockets provides pluggable event-loop backends (`WITH_IO_URING`, `WITH_LIBUV`, `WITH_ASIO`, `WITH_GCD`; upstream `uNetworking/uSockets`). The **default Linux backend is its own native epoll loop** (uSockets ships a hand-written epoll/kqueue `us_loop` rather than going through libuv); io_uring is an *opt-in* compile-time backend (`LIBUS_USE_IO_URING`, tracked as a low-priority experiment in uWebSockets issue #1603). The TechEmpower image (`node:20-slim`, `npm install` of the prebuilt `uWebSockets.js#v20.44.0` binary) uses the **default epoll** backend — io_uring is not enabled here. Importantly uWebSockets does **not** use Node's own libuv loop; it installs its native loop and (in non-cluster integration) can adopt libuv, but the addon runs its own epoll loop per worker.
- **Worker/process model:** `node:cluster` + `SO_REUSEPORT`. Each forked worker calls `webserver.listen(...)`; the kernel load-balances accepted connections across the per-process listen sockets. Worker count = logical core count. No explicit CPU pinning in the vendored config (relies on the kernel scheduler + reuseport hashing); the Dockerfile sets only `NODE_ENV=production` and `CMD ["npm","start"]` → `node src/clustered.js`. No extra V8/node flags.
- **HTTP parser:** uWebSockets' own zero-copy C++ HTTP/1.1 parser (string views into the receive buffer). It supports **HTTP pipelining** and, crucially, **write corking**: `response.cork(cb)` batches every `writeStatus`/`writeHeader`/`end` inside the callback into a **single `send()` syscall** (upstream `misc/READMORE.md`: those calls "only result in one single send syscall" when corked; uncorked they "perform very bad and use excessive networking"). The engine auto-corks within its own callbacks, so the precomputed plaintext path is already a single batched write.

## Performance techniques (catalog)

- **Precomputed responses (`DeclarativeResponse`)** — the entire plaintext route is `new uWebSockets.DeclarativeResponse().writeHeader("Server","uWS").writeHeader("Content-Type","text/plain").end("Hello, World!")`, built once at boot (`research-sources/05-uwebsockets.js/src/server.js:21-25`). At request time the C++ engine replays a prebuilt byte buffer with no JS callback, no per-request header formatting, and no V8 round-trip. This is the single biggest reason a "JavaScript" framework lands in the plaintext top-5.
- **Write corking → syscall amortization** — `response.cork(() => { ...writeHeader...; response.end(...) })` collapses status line + all headers + body into one `send()` (used on every dynamic route in `server.js`; mechanism documented at uWebSockets `misc/READMORE.md`). One TCP segment per response instead of several — the same lever jai-http reaches for with `writev`.
- **HTTP pipelining + response coalescing** — under TechEmpower's pipelined plaintext load, the C++ parser reads multiple requests out of one recv buffer and the engine can coalesce their corked responses into far fewer `send()` calls. This batching across pipelined requests is what separates ~28M-class leaders from ~1–2M non-pipelining servers.
- **Server-set Date header in C++** — `utils.js:6-8` documents that the `Date` header is added automatically by uWebSockets in C++ (`HttpResponse.h`), not by JS. uWebSockets timestamps/caches the date string at the engine level rather than formatting it per request in script.
- **Multi-core via `SO_REUSEPORT`** — `clustered.js` forks N workers, each with its own reuseport listen socket and event loop; shared-nothing, no inter-worker coordination (`research-sources/05-uwebsockets.js/src/clustered.js:5-23`).
- **Native epoll loop (libuv bypass)** — uSockets runs its own tight epoll `us_loop` per worker rather than dispatching through Node/libuv, removing a layer of indirection on the I/O path (uSockets backends in `uNetworking/uSockets`). io_uring is available as an opt-in backend but is *not* the default and not enabled in this image.
- **Faster JSON / sorting (dynamic routes only)** — `slow-json-stringify` precompiles a serializer from a fixed schema (`utils.js:1,66-67`) instead of generic `JSON.stringify`; a hand-rolled insertion sort (`sortByMessage`) avoids comparator-callback overhead for the small fortunes array. Not on the plaintext path.
- **Build/runtime** — prebuilt native binary (`uWebSockets.js#v20.44.0`) so the C++ engine isn't recompiled; `_cfg('silent')` disables logging; V8 JIT compiles the (minimal) remaining JS. `node:20-slim`, production env.

## What's reusable for jai-http

- **(a) Already done** — `SO_REUSEPORT` shared-nothing workers each with their own epoll loop is *exactly* jai-http's model; uWebSockets validates it at the top of the charts. Zero-copy HTTP parsing: also already done. Single-`writev` response (jai-http) is the equivalent of one corked `send()`.
- **(b) Portable + HIGH leverage:**
  - **Precomputed responses (`DeclarativeResponse` analogue).** For static/constant routes (and the benchmark's plaintext route specifically), build the full status-line + headers + body byte buffer **once at registration time** and have the worker `writev`/`send` it verbatim — skipping per-request header formatting entirely. jai-http already pays per-request to format the header (the temp-storage/Pool work in the perf-collapse fix); a precomputed buffer for constant responses removes that cost to ~0 and is the closest direct analogue to what puts uWS in the top 5.
  - **Pipelining + response coalescing.** This is the explicit gap in jai-http's "not yet doing" list and the real distance between ~1.8M and ~28M on TechEmpower plaintext. Map onto the existing epoll/Pool/`writev` design: when an edge-triggered read drains multiple pipelined requests from the connection buffer, dispatch them all, then emit **one `writev`** of the concatenated responses (an iovec array of all per-request buffers) instead of one `writev` per request. Corking is conceptually jai-http's `writev`/response-coalescing lever applied *across pipelined requests in a batch*, not just across header+body of one response.
  - **Cache the Date header string.** uWebSockets formats `Date` once in C++ and reuses it. jai-http can compute the RFC1123 date once per second (per worker) and memcpy it into outgoing headers — cheaper than formatting per request, and a prerequisite for cheap precomputed responses that still need a fresh-ish date.
- **(c) Portable, lower leverage** — schema-precompiled JSON serialization (jai-http's `modules/json` parses per-instance; a per-type compiled serializer would mirror `slow-json-stringify`); but this only matters for the `/json` route, not plaintext, so it's a smaller lever.
- **(d) Not portable (V8/JS-specific)** — `DeclarativeResponse` as an *API shape* exists to dodge the JS↔C++ boundary cost; jai-http has no such boundary, so the *motivation* is weaker, but the underlying *technique* (precomputed response buffer) still applies. V8 JIT, `cluster` process forking semantics, and `slow-json-stringify`'s codegen are JS-runtime specifics, not directly portable.
- **io_uring data point:** uSockets offers io_uring as an *opt-in* backend but defaults to epoll, and upstream notes io_uring's network-I/O win over a well-tuned epoll loop is typically <10% (often <5%) — i.e. epoll is not jai-http's bottleneck; pipelining/coalescing and precomputed responses are far higher leverage than switching event-loop backends.

**Highest-leverage takeaways for jai-http:**
1. **Implement HTTP/1.1 pipelining with response coalescing** — drain all pipelined requests from one edge-triggered read and emit a single `writev` of all responses. This is the headline gap and the main reason leaders hit ~28M.
2. **Precompute constant-route responses** (a `DeclarativeResponse`-style baked byte buffer) so the plaintext/static path does zero per-request header formatting — `writev` a ready-made buffer.
3. **Cache the `Date` header once per second per worker** rather than formatting it per request (enables #2 while staying spec-compliant), mirroring uWebSockets' C++ Date handling.
